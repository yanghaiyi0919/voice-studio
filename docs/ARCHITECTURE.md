# 架构与数据流程

## 分层

UI 只组织录音、确认与展示。SpeakerService 负责录音质检、模型调用、档案更新和文件生命周期；SpeakerStore 负责事务与持久化。ModelHub 封装 CAM++、emotion2vec 和 Vosk，使用推理锁管理共享模型。

~~~mermaid
flowchart TD
    A[录音或上传多段参考语音] --> B[解码、16 kHz 单声道与基本质检]
    B --> C[CAM++ 提取并归一化逐段声纹]
    C --> D[一致性检查与平均声纹]
    D --> E[SQLite 原子保存档案与声纹]
    F[新录音] --> G[提取声纹并读取当前档案快照]
    E --> G
    G --> H[余弦相似度与候选分差]
    H --> I[确认身份或暂不确认]
~~~

## 登记与更新

新登记需要 3–20 段不同录音；追加允许少量新片段，更新后仍需 3–20 段。每段声纹先归一化，再平均并归一化为参考向量。声纹之间差异过大时阻止提交，但这项检查不能完全识别混入的其他说话人。

保存过程中，任一重复录音、无效向量或过期版本都会使数据库事务回滚。前端保留录音选择，方便用户修正。模型权重的 SHA-256 标识随档案保存，防止不同模型的特征混用。

同一份内容标准化为 PCM 后计算指纹，用于阻止完全重复的参考录音。它不是音频感知去重，不能识别所有剪辑或有损转码变体。

## 拒识与校准

接受身份需要同时满足：最高余弦分数达到门槛；存在第二候选时，最高与第二分数之差也达到门槛。空库、模型不匹配、无效音频分别返回明确状态。

内部校准对每个用户逐段留一：同人分数使用其余录音形成的参考向量，异人分数取其他用户参考向量中的最高值。选择满足目标误接受率的候选门槛，再兼顾内部误拒率和分布间隔。结果包含模型、档案版本指纹、试验数与时间。

这仍然使用登记数据，同房间、同设备和相同说话内容可能使估计偏乐观。独立的陌生人、跨设备和攻击样本验证需另行构造；不能由内部校准推出安全认证能力。

## 数据生命周期

SQLite 保存姓名、用户 ID、逐段向量、平均向量、质量摘要、更新版本和阈值。默认不保留登记录音；勾选后才保存归一化录音。删除档案会级联删除样本向量，并只清理由该应用保存的录音文件，路径检查限制在本机 private/audio 内。

数据库时间保留带时区的 UTC 格式；档案列表与详情统一转换为北京时间（UTC+8），显示为 YYYY-MM-DD HH:mm:ss，并注明时区。

原始导入来源、压缩包和用户自己选择的文件不由删除档案操作修改。分析音频和浏览器缓存位于 runtime 中，属于本机私人运行数据；Gradio 上传缓存按每十分钟检查、清理超过一小时的缓存文件。应用自己生成的分析音频和输出仍可能保留在 runtime 中，清理时应先停止程序。

本应用面向本机使用，没有多用户登录隔离。SQLite 和录音文件不加密，请使用受保护的操作系统账户管理本地数据。

页面文件下载只额外开放生成结果目录。声纹目录、模型、旧录音来源、日志与 Git 元数据加入文件接口阻止列表，避免被误作为音频结果返回。
